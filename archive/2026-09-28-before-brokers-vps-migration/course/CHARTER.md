# Distributed AI Agent Systems — course charter

Adopted September 28, 2026. This is the current teaching agreement. The [roadmap](../ROADMAP.md) defines curriculum; [decisions](../teaching/DECISIONS.md) records why it changes.

## Destination and scope

Learn to design, build, evaluate and operate reliable distributed AI agent systems, and explain the model-serving layer they depend on. The program has four stages: foundations, reliable single-host systems, distributed systems and integrated capstone. Applied graduate-level depth means understanding mechanisms, reading selected authoritative sources, conducting controlled experiments and defending choices. Foundations are taught when needed; rigor is demonstrated at assessment rather than assumed from the course title.

Protected core: engineering practice (Git/GitHub, review, testing, design decisions, recovery and acceptance); programming/agent internals; operating systems/Linux; networks/VPS operations; containers/Kubernetes; model inference/serving; distributed state, coordination and reliability. These topics can evolve through an explicit agreed revision. A new tool or interesting project alone does not displace them.

Kernel development, implementing a complete network stack and model pretraining are optional specializations. Research/source reading supports learning outcomes; finishing every linked resource is not a graduation condition. Retain existing language-course completion goals separately from capability assessments.

## Workload and teaching rhythm

Total capacity is **15 focused hours/week**, normally 10 core study/labs, 3 course-project work and 2 exploration. Assessments and review are included. Count shared work once. Unused exploration time returns to core work. No additional build lane is implied.

Keep one primary learning module and one active course project. A lab may be the practical work of that module, not a second independent project. Observe the vault's global project limits as well. Each execution project must have a useful deliverable within 21 calendar days at its allocated capacity. A three-hour/week project slot supplies at most nine hours across three weeks; split larger proposals instead of giving them implausible dates. A milestone or stage may contain several projects.

At the weekly review, inspect actual evidence and hours, pick the next core question, project slice and exploration, and name displaced work. At milestone boundaries, assess mastery and review the forecast. Detailed near-term assignments follow observed prerequisites; later stages remain forecasts. Existing deadline changes require the review below. There is no agreed finish date or total-hour estimate for the expanded program.

Prepare one concrete learning question, ask for a prediction/attempt, give targeted explanation and feedback, then use a small source reading or experiment. Expand the active module rather than generating the whole course's lessons or solving the student's exercises in advance.

## Adapting the course

The core is protected from accidental drift, not frozen forever. Any agreed part can be revised deliberately.

1. Capture the request in [IDEAS.md](IDEAS.md), including its intended learning or practical value.
2. Compare it with the current milestone: same outcome with another exercise, an elective, or a change to required scope? Estimate prerequisites, hours, project-slot use and affected deadlines. State uncertainties.
3. For routine substitutions, record the reason and continue. For required-scope or deadline changes, show the concrete before/after impact and obtain agreement once. An explicit student instruction to add a named topic authorizes that scope addition: record the request and implement its placement without asking the same permission again. Ambiguous scope and changes to existing agreed deadlines still require clarification or review.
4. After agreement, update the authoritative roadmap and affected project/material mappings together. Adjust the owning Obsidian schedule only within the agreed change. Preserve annotations, checkboxes, completion records and evidence.
5. Append the decision and its rationale to the decision record. Record old-to-new milestone mapping and any remaining gaps. Existing evidence stays credited for the capabilities it demonstrates; do not erase completion or claim it proves newly added skills.

Milestone IDs are stable references. Add a new ID for a new destination; retire IDs with a pointer rather than reusing them. Small clarifications can keep an ID; material acceptance-criteria changes carry a dated decision. Snapshot replaced plans before structural changes. Large revisions can be discussed with grill-with-docs; everyday ideas use the lightweight intake process.
